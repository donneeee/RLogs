# Automarker packet-substitution feasibility audit

This is a strictly read-only, offline audit of whether a legitimate outbound
ground-marker request could be changed in place without changing its byte
length. It uses only the existing sanitized build-25247556 proofs and parser
code. It did not capture traffic, alter a packet, create an injector, or test
anti-cheat behavior. The machine-readable result is
`plugins/games/blue-protocol-star-resonance/research/game-file-inventory/global/steam-25247556/ground-marker-packet-substitution-feasibility.v1.json`.

## What the evidence proves

The observed application request is a protobuf `World.Types.UseSlot` wrapper.
Its marker identity is represented twice: `UseSlotRequest.slot_id` is 201–206
and `UseSkillParam.skill_id` is 1101–1106. Both ranges use two-byte protobuf
varints, so changing one valid marker identity to another while changing both
fields preserves their encoded widths. Target and current positions are nested
`Position` messages containing four `fixed32` values. Any finite replacement
bit pattern also occupies four bytes, so changing XYZ does not alter the
protobuf length.

For all six sanitized observations, the other width-sensitive values also stay
within one width band: the positive action UUID occupies five varint bytes, the
begin time occupies six, and `sessionSequence` occupies two. Together with the
80-byte authenticated attribute envelope, the observed message shape derives
to 66 bytes for `UseSkillParam`, 158 bytes for `UseSlotRequest`, and 161 bytes
for the outer protobuf wrapper. A deterministic unit test checks those lengths
for all six observations and for changed fixed32 coordinates.

The authenticated attribute envelope is separate from both position messages.
It is 16 bytes of IV, 32 bytes of HMAC-SHA256, and 32 bytes of AES-CBC
ciphertext; the HMAC covers the IV and ciphertext. Therefore an edit limited to
the marker identity and position fields does not directly invalidate that
inner HMAC. This does not prove that the server accepts the resulting semantic
combination.

## Envelope layers

The application message is not a standalone TCP payload. The observed route is
a nested `Call` under `FrameUp`:

1. TCP byte stream (possibly split or retransmitted across physical packets).
2. Outer six-byte BPSR frame header: big-endian total length plus a big-endian
   fragment value whose high bit is the zstd flag.
3. `FrameUp` payload: a four-byte frame sequence followed by nested frames.
4. Nested six-byte BPSR `Call` header.
5. Twenty-byte big-endian route header: service, stub, call ID, and method.
6. The 161-byte protobuf application message for the observed width band.

The sanitized correlation proof does not retain the outer or nested compression
flags, complete frame lengths, batching, TCP segmentation, or retransmission
layout. Consequently it does not prove that the 161 application bytes appear
uncompressed at stable wire offsets. If either applicable zstd flag is set,
recompression can change wire length even when protobuf length is unchanged.

The parser exposes no BPSR frame checksum. That is evidence only about the
decoded grammar, not proof that no validation exists elsewhere. At the network
layer, any raw-byte rewrite would at minimum require correct IP/TCP checksums,
suppression of the original packet, and consistent treatment of retransmitted
bytes. Equal payload length would avoid shifting subsequent TCP sequence and
acknowledgement numbers; it would not supply those missing inline-transport
capabilities.

## Fresh state and divergence risks

One-for-one substitution can preserve values already generated by the game,
but it cannot prove that they remain valid for changed semantics. The action
UUID, begin time, `sessionSequence`, authenticated attributes, RPC call ID, and
`FrameUp` sequence are live game-owned state. The six-marker trace also shows
that the sequence spaces are shared with unrelated traffic.

Changing a request after the client has locally initiated a different marker or
target can split client prediction from server authority. Server-side checks
may compare slot-to-skill identity, target range or raycast results, current
position, cooldown/eligibility state, and the authenticated attributes. The
client may also await state for the action it actually initiated. None of those
acceptance or reconciliation rules is proven by a successful passive decode.

## Capture implementation boundary

RLogs' Windows Npcap adapter is sniff-only in the executable code path: it loads
`pcap_open_live`, `pcap_next_ex`, filtering, datalink, error, and close APIs,
but no send API. `Packet.dll` send exports occur only in dependency compatibility
validation and are never bound or called. The repository contains no WinDivert
implementation and no inline drop, rewrite, retransmission, or checksum engine.

## Verdict and next evidence

Application-level byte-length preservation is proven for changing marker
1–6 and fixed32 XYZ within the observed value-width bands. Live one-for-one
substitution is not proven safe or feasible at the wire boundary, and no sender
should be enabled from this result.

The next non-invasive step is an offline receipt generated from the already
retained private capture. For each of the six requests it should publish only:

- outer and nested compression flags and frame lengths;
- the number and lengths of nested frames in each `FrameUp` container;
- application offset/length after decoding;
- TCP segment-count and retransmission/overlap classifications, without
  addresses, ports, sequence numbers, payloads, or identifiers;
- whether changing only the two marker varints and selected fixed32 values can
  be demonstrated to preserve each uncompressed container length in a purely
  synthetic replay buffer.

That receipt would settle wire-layout uncertainty without new live traffic or
packet modification. It still would not establish server acceptance,
anti-cheat safety, or permission to transmit.

The offline-only sanitizer is now available for that retained evidence:

```powershell
cargo run -p rlogs-game-bpsr --bin rlogs-bpsr-automarker-wire-layout-receipt -- `
  --private-research `
  --captured-build 25247556 `
  --unverified-carry-forward-pack-source-build 24687926 `
  --pack plugins/games/blue-protocol-star-resonance/protocol-packs/global/steam-24687926/pack.json `
  --connections "<private>\connections.json" `
  --journal "<private>\protocol.jsonl" `
  --output "<private>\wire-layout-receipt.json" `
  "<private>\capture.pcapng"
```

It accepts either a journal made with the exact reviewed pack or a journal
whose header explicitly records a non-runtime-authoritative carry-forward pack.
The request itself is still decoded only through the exact build-25247556
automarker decoder. Output creation is fail-if-present and the receipt contains
no payloads, endpoints, ports, TCP sequence numbers, call IDs, session/action
identifiers, timestamps, or local paths.
